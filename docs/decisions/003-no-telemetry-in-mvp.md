# 003. MVP 에는 출시 후 지표 수집 경로를 두지 않는다

- 날짜: 2026-11-11
- 상태: 결정 (MVP 범위) — **출시(2027.3 가정) 전 재설계 필요**
- 관련: `docs/db/erd.data.mjs` — `card_stat_daily` 삭제, 앱 → 서버 이동 없음

## 배경

- 기획 6번은 출시 후 첫 개정(2027.4.14)에서 아래 지표를 측정한다고 약속한다
  - MAU = 유지 설치 수 × 월간 능동 비율
  - 시행 직전 확인률 (목표 30%), 안내 재반응률 (목표 60%), 6개월 수신 유지율 (목표 80%)
  - '확인된 안내 없음' 응답 비율, Gleo 일치율
- 이 지표의 원천인 확인 이력·알림 기록은 **차량 DB 에만** 있다 (DB 분리 원칙: 운전자 기록은 차 밖으로 안 보냄)

## 결정

- MVP 에는 차 → 서버 지표 전송과 집계 테이블을 두지 않는다
- 차 → 서버로 가는 데이터는 주차 중 자유 질문 문장(매칭용)뿐이다

## 이유

- **PT·MVP 동작에 필요 없다**: 지표는 출시 후에만 쓰인다
- **정할 것이 먼저 있다**
  - MAU 는 '서로 다른 사용자 수'라 가명 기기 ID 가 있어야 센다 — "운전자 기록은 차 밖으로 안 보냄" 원칙과 부딪힌다
  - 집계 단위(카드별 일 합계 vs 이벤트), 동의 고지 문구, 보관 기간이 정해지지 않았다
- 정하지 않은 채 테이블만 만들면 데이터가 들어올 경로 없는 빈 테이블이 된다 (이전 ERD 의 `card_stat_daily` 가 그랬다)
- 나중에 더해도 기존 구조를 깨지 않는다 (새 테이블 + 새 API 추가)

## 영향

- 출시 전까지 기획 6번 지표 중 아래는 **측정할 수 없다**
  - MAU, 시행 직전 확인률, 안내 재반응률, 수신 유지율 — 차량 기록이 필요
- 지금 구조로 측정 가능한 것
  - 서버 자유 질문 매칭 실패 비율 — `review_request` 건수로 근사 (Gleo 경로는 제외)
  - Gleo 일치율 — DB 가 아니라 녹음 대조 테스트 (기획 3번)
- 기획서 6번의 측정 계획은 그대로 두되, 수집 설계가 출시 전 과제임을 팀이 알고 있어야 한다

## 다시 검토할 때

- **출시 일정 확정 시 (늦어도 2027.3 이전)** — 첫 개정 2027.4.14 측정에 맞추려면 그 전에 배포돼야 한다
- 정할 것
  - 가명 기기 ID 사용 여부와 생성·폐기 방식 (렌터카 모드 포함)
  - 보낼 데이터의 범위: 카드별 확인 여부만? 단계·시각까지?
  - 동의 고지 시점과 문구, 거부 시 동작
  - 서버 보관 기간
