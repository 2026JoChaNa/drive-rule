# 011. 법령 개정 자동 수집 — 국가법령정보 Open API 로 '분류 대기' 개정을 쌓는다

- 날짜: 2026-11-13
- 상태: **채택** (서버). 운영 연결은 인증값(OC) 발급 · IP 등록 뒤
- 기준: Notion 「🚦 기획 v6」 기능 ⑦ (법령 개정 → 일반 운전자 해당분만 카드로), 결정 [001](001-remove-driving-context.md) · [004](004-card-lifecycle.md) · [008](008-server-api-v1.md) 3번 ('Open API 연동은 이번 범위 밖 — CMS 가 손으로 등록')
- 관련: [docs/content/pt-cards-legal-check.md](../content/pt-cards-legal-check.md) — 사람이 개정을 찾아 대조한 기록 (2026-11-12)

## 배경

지금은 CMS 가 법령 개정(`law_revision`)을 손으로 등록한다. 2026-11-12 시연 카드 대조에서
시행규칙 별표 28 개정(행정안전부령 제636호, 2026.8.24 공포)을 사람이 개정문 목록을 훑어서야 찾았다.
카드 A 과태료 금액도 시행령 개정이 공포되는 날을 누군가 지켜봐야 채울 수 있다.
→ 서버가 공포된 개정을 스스로 찾아 **분류 대기(PENDING)** 로 올려 두면, 사람은 분류와 카드 작성만 하면 된다.

## 조사 (2026-11-13)

| 사실 | 값 | 영향 |
|---|---|---|
| 목록 API | `GET https://www.law.go.kr/DRF/lawSearch.do?target=eflaw` (시행일 법령 목록). 요청 `OC`(필수) · `type=JSON` · `LID`(법령ID) · `nw`(1 연혁 · 2 시행예정 · 3 현행) · `ancYd`(공포일 범위 `yyyyMMdd~yyyyMMdd`) · `sort=ddes` · `display`(최대 100) · `page` | 법령 하나씩, 공포일 범위로 묻는다 |
| `target=law` 와 차이 | `law` 는 **현행 1건**만. 공포됐지만 시행 전인 개정(카드 A 의 법률 제22067호처럼)은 `eflaw` 의 `nw=2` 에만 있다 | `eflaw` + `nw=1,2,3` |
| 응답 칸 | `LawSearch.totalCnt` · `LawSearch.law[]` — `법령일련번호` · `법령명한글` · `법령ID` · `공포일자` · `공포번호` · `제개정구분명` · `법령구분명` · `시행일자` · `현행연혁코드` 등 (공식 안내 화면) | 아래 '저장하는 값' |
| 응답 모양 | 결과가 **1건이면 `law` 가 객체**, 여러 건이면 배열. 숫자도 문자열로 온다. `공포번호` 는 앞에 0 이 붙는다(`08635`) | 둘 다 받아 한 모양으로 바꾼다 (공개 구현 2곳에서 확인) |
| 한 공포 = 여러 행 | `eflaw` 는 시행일별 판이라 시행일이 나뉜 개정은 **같은 공포번호가 여러 행**이다 | 공포번호로 묶어 1건으로 |
| 인증 실패 | HTTP 200 + `{"result":"사용자 정보 검증에 실패하였습니다.","msg":"…서버장비의 IP주소 및 도메인주소를 등록해 주세요."}` (2026-11-13 `OC=test` 로 실제 호출해 확인) | `LawSearch` 가 없으면 실패로 본다. **운영 EC2 IP 를 신청 화면에 등록해야 한다** |
| 법령ID | 도로교통법 `001638` · 시행령 `003395` · 시행규칙 `007079` (국가법령정보센터 화면에서 확인) | 기본 감시 대상 |
| 관보 공포 → 센터 반영 | 보통 공포 당일~며칠 | 하루 한 번이면 충분 |

인증값이 없어 **실제 성공 응답은 아직 받아 보지 못했다.** 테스트 픽스처는 공식 안내의 칸 이름과 위 모양으로 만들었다.
처음 운영에 연결할 때 수동 수집 결과를 보고 픽스처를 실제 응답으로 바꾼다 (아래 '연결 순서' 4).

## 결정

### 1. 개정 기록만 만들고, 카드 초안은 만들지 않는다

- 수집기는 `law_revision` 행을 **PENDING** 으로 넣는 데서 멈춘다
- 시행령 · 시행규칙 개정은 대부분 면허 · 학원 · 서식 같은 일반 운전자와 무관한 내용이다 (2026년 시행규칙 개정 3건 중 운전자 안내로 이어질 만한 것은 제636호의 긴급자동차 벌점 신설 하나 — 나머지는 약물 측정 절차 · 적성검사 · 면허시험).
  개정마다 카드 초안을 만들면 검수 대기열이 빈 카드로 찬다 — 기능 ⑦ '일반 운전자 해당분만'은 **분류가 먼저**다
- 카드는 지금처럼 사람이 APPLICABLE 로 분류한 개정에 붙여 CMS 에서 쓴다

### 2. 무엇을 · 언제 · 얼마나

| 항목 | 값 | 설정 |
|---|---|---|
| 감시 법령 | 도로교통법 · 시행령 · 시행규칙 | `LAW_SYNC_LAW_IDS` (기본 `001638,003395,007079`) |
| 주기 | 매일 06:30 (Asia/Seoul) | `LAW_SYNC_CRON` |
| 범위 | 오늘부터 **90일 전**까지 공포된 개정. 단 `LAW_SYNC_SINCE`(기본 2026-10-01) 이전은 보지 않는다 | `LAW_SYNC_LOOKBACK_DAYS` · `LAW_SYNC_SINCE` |
| 꺼짐 | `LAW_API_OC` 가 비어 있으면 예약 실행을 하지 않는다. 서버는 정상 기동한다 | — |

- 90일을 다시 보는 이유: 서버가 며칠 꺼져 있었거나 센터 반영이 늦어도 다음 실행에서 줍는다. 이미 있는 것은 건너뛰므로 다시 봐도 안전하다
- `SINCE` 를 두는 이유: 처음 켤 때 수십 년 연혁이 한꺼번에 대기열에 들어오지 않게. 2026-10-01 은 손으로 넣은 법률 제22067호(2026.10.13) 바로 전이다

### 3. 저장하는 값 (스키마 변경 없음)

| 칸 | 값 | 예 |
|---|---|---|
| `law_no` | `제{공포번호}호` — 앞의 0 을 뗀다. **기존 손 등록과 같은 형식** | `제36728호` |
| `law_name` | `{법령명한글} {제개정구분명}` | `도로교통법 시행령 타법개정` |
| `source_key` | `LAWGO-{법령일련번호}` — 같은 공포의 여러 판 중 공포일이 같고 시행일이 가장 이른 판 | `LAWGO-290387` |
| `promulgated_on` | `공포일자` | `2026-09-29` |
| `triage_status` | `PENDING` | |

- **중복 판단 = `law_no`** (이미 UNIQUE). 손으로 넣은 `제22067호`(`MANUAL-22067`)도 같은 번호라 다시 들어오지 않는다
- 동시에 두 번 돌아 UNIQUE 에 걸리면 그 행은 '이미 있음'으로 센다
- CMS 응답에 `sourceUrl` 을 더한다 — `LAWGO-` 행이면 `https://www.law.go.kr/LSW/lsInfoP.do?lsiSeq={법령일련번호}` (분류하는 사람이 바로 원문을 연다). 손 등록 행은 `null`

알고 있는 한계: 공포번호는 법령 종류(법률 · 대통령령 · 부령)마다 따로 매긴다. 서로 다른 종류가 같은 번호를 가지면 뒤에 온 것이 '이미 있음'으로 빠진다.
지금 번호대는 법률 2만 2천 · 대통령령 3만 6천 · 부령 6백대라 감시 3개 법령에서 겹치려면 수십 년이 걸린다. 겹칠 때가 오면 `law_no` 에 종류를 붙이는 마이그레이션을 한다.

### 4. 실패 처리

- 법령 하나가 실패해도 나머지는 계속한다. 결과는 법령별 `OK` / `FAILED` + 새로 넣은 수 · 이미 있음 수 · 사유
- 실패 사유: 인증 실패(위 `result`/`msg` 그대로) · JSON 아님 · 연결 · 시간 초과(연결 5초 · 응답 10초)
- 페이지는 100건씩, 최대 10쪽. 90일 안에 한 법령이 100건을 넘을 일은 없다
- 서버가 `ancYd` 범위를 무시하고 전체를 돌려줘도 어긋나지 않게, 받은 뒤 공포일로 한 번 더 거르고 공포일 내림차순 목록에서 범위보다 오래된 행이 나오면 다음 쪽을 묻지 않는다
- **로그 · 오류 문장에 OC 값을 남기지 않는다** — 요청 주소가 섞인 예외 문장은 `OC=***` 로 바꾼다

### 5. 수동 실행 — `POST /api/v1/admin/law-revisions/sync`

- CMS 키(`X-Admin-Key`)로 지금 바로 한 번 돌린다. 응답은 위 결과 그대로
- `LAW_API_OC` 가 없으면 **503 `LAW_API_NOT_CONFIGURED`**
- 쓰임: 인증값을 넣은 직후 연결 확인, 큰 개정 공포 당일 기다리지 않고 받기

## 연결 순서 (사람이 할 일)

1. open.law.go.kr → Open API 신청. **서버 IP `13.124.175.42` 를 등록**한다 (로컬 PC 에서 쓰려면 그 IP 도)
2. 승인 뒤 받은 OC 값을 EC2 `~/drive-rule/.env` 의 `LAW_API_OC=` 에 넣고 `./dc.sh up -d app` (값은 채팅 · 커밋에 남기지 않는다)
3. `POST /api/v1/admin/law-revisions/sync` → 세 법령 모두 `OK` 인지 본다. 2026-10-01 이후 공포분(예: 시행령 대통령령 제36728호)이 PENDING 으로 들어온다
4. 받은 실제 응답 한 건으로 테스트 픽스처를 바꾼다

## 고르지 않은 것

| 안 | 이유 |
|---|---|
| 개정마다 카드 초안 자동 생성 | 위 결정 1 — 대부분 해당 없음. 분류가 먼저 |
| 개정문 · 신구조문 본문까지 저장 | 분류하는 사람은 `sourceUrl` 로 원문을 연다. 본문 API(`lawService.do`) 구조는 인증 뒤 확인하고, 카드 작성 보조가 필요해지면 그때 |
| 국가법령정보센터 화면(`lsRvsDocListP.do`) 긁기 | 키 없이 되지만 화면이 바뀌면 깨지고 공식 이용 경로가 아니다. 2026-11-12 대조 때 사람이 쓴 것은 일회성 |
| 감시 법령을 DB 에 두고 CMS 로 관리 | 세 개이고 거의 안 바뀐다. 환경변수로 충분 |
| 공포일 대신 '마지막 실행 이후'만 보기 | 상태(마지막 실행 시각)를 저장해야 하고, 놓친 날을 줍기 어렵다. 고정 창 + 중복 건너뛰기가 단순하다 |
